Datadog, Block, and Cloudflare All Abandoned the Default MCP Pattern. Here’s What They Use Instead

Comparing traditional, code mode, and layered query patterns — with real benchmarks on the HackerNews API

Tanmay Deshpande
7 min read
·
Mar 13, 2026
--
I built three MCP servers for the same API — the HackerNews API — each using a different architectural pattern.
The traditional approach (one tool per endpoint, 10 tools) consumed 6,624 tokens and 3.6 seconds across five benchmark scenarios.
The two alternative patterns — code mode and layered query — each cut tokens by about 65%, and the layered approach finished in 2.0 seconds flat. In one scenario, the token reduction was 98%.
These aren’t theoretical numbers. They’re measured against the live HN API with cl100k_base token counts.
The most popular MCP server pattern today looks like this: take your REST API,
wrap every endpoint as a tool,
ship it.
It’s a weekend project. I know, because that was my v1.
The server runs fine. The agent calls the tools. But then it fills its context window with data it didn’t need, chains 11 sequential tool calls for a question that should take one, or asks the LLM to mentally compute averages over 40 raw records.
Three companies — Datadog, Block (Square), and Cloudflare — independently built production MCP servers and all abandoned the thin-wrapper approach.
I wanted to see if their design principles held up with real measurements. So I built all three patterns and benchmarked them.

The Experiment

I wrapped the HackerNews API three ways:
v1 — Traditional: 10 tools, one per endpoint. get_top_stories, get_item, get_user, etc. Exactly what most MCP tutorials tell you to build.
v2 — Code Mode: 1 tool (execute_code). The LLM writes Python against a pre-defined hn API object. All chaining, filtering, and computation happen server-side. Inspired by Cloudflare's approach.
v3 — Layered + Query: 3 tools. A discover() tool for progressive disclosure, a flexible query() tool with field selection, filtering, sorting, aggregation, and format control, plus a compare() tool for cross-resource analysis. Combines Block's layered pattern with Datadog's context-efficiency practices.
Then I ran five scenarios of increasing complexity.
For simple queries — “show me the top 5 stories” — all three patterns are comparable.
v1 uses 284 tokens in 0.40s, v3 uses 259 tokens in 0.29s, v2 uses 389 tokens in 0.29s (the code string costs more tokens than a tool name + params).
No drama.
The interesting results start when queries get even slightly complex.

Multi-hop fan-out: “Top 5 stories with author karma.”

This requires fetching a story list, then each story’s details, then each author’s profile. v1 needs 11 sequential tool calls, burns 1,578 tokens, and takes 1.69 seconds of server time — most of it intermediate data the agent doesn’t need for the final answer. v2 collapses this into a single script: 227 tokens in 0.88s, an 86% reduction. v3 lands at 288 tokens (82% savings) in just 0.13 seconds, using 6 calls with field selection (fields='id,title,score,by') and CSV formatting to keep each response lean.
The mechanism is different but the savings are similar. v2 eliminates round-trips entirely. v3 can’t avoid the fan-out calls but compensates by trimming each response down to only the fields the agent needs — and because trimmed payloads parse faster, it’s actually the quickest of the three.

Aggregation: “Compare average scores of Ask HN vs Show HN.”

This is where v3 dominates. v1 returns all 40 stories raw — 1,891 tokens — and expects the LLM to mentally compute averages. Error-prone and wasteful. v2 writes a Python script to do the math: 224 tokens. But v3’s purpose-built compare() tool does it in a single call with 17 request tokens and returns just two lines: 47 total tokens.
That's a 98% reduction over v1.
Here’s the full picture:
Both v2 and v3 achieve ~65% total token savings over v1.
v3 is fastest overall (2.00s) despite more calls than v2, because trimmed responses reduce per-call overhead.
At scale (1,000 queries/day on Claude Sonnet pricing), that’s roughly $2,900/month for v1 vs ~$900/month for either alternative.
One critical caveat: these wall times measure only server-side execution.
In a real LLM conversation, each tool call also incurs LLM API round-trip latency — typically 0.5–3 seconds per call. That means v1’s 17 total calls could add 8–51 seconds of LLM latency on top, while v2’s 5 calls add only 2.5–15 seconds. This makes call count matter even more than the server-side numbers suggest.

Treat MCP server as a middleware layer, not a passthrough.

The upstream API — whether it’s yours or a third party’s — returns whatever it returns. Usually JSON, with every field included. You don’t control that. But you control what the MCP server hands to the agent.
v3 demonstrates this most clearly. The HN API has no query language, no field selection, no aggregation, no CSV output.
The MCP server provides all of that by fetching data from the API, processing it internally, and returning only what the agent needs in the most token-efficient format. The agent sees a rich query interface.
The underlying API is unchanged.
This is the mental shift. The MCP server isn’t a translation layer between your API and the agent. It’s an agent-optimized interface that happens to use your API as a data source.

What the Industry Converged On

The benchmarks validate the design principles that Datadog, Block, and Cloudflare arrived at independently:
Context-efficient output (Datadog technique): CSV default format, field selection, and data trimming. In the benchmarks, v3’s fields='id,title,score,by' with CSV formatting cut response tokens by 88% compared to v1's full-payload responses in Scenario 3.
The MCP server re-serializes upstream JSON — the API doesn't need to change.
Layered progressive disclosure (Block technique): v3’s discover() tool lets the agent learn what's available without bloating the system prompt. Block compresses 200+ Square API endpoints into 3 tools with the same pattern: Discovery → Planning → Execution. The benchmarks show this scales — 3 tools covered every scenario that v1 needed 10 for.
Code mode for complex chains (Cloudflare technique): v2 is unbeatable for multi-hop joins (86% savings, 1 call vs 11). LLMs are strong code generators — they’ve seen millions of real Python/TypeScript files in training, but only synthetic tool-call examples. The tradeoff is a -37% penalty on simple queries (code overhead exceeds tool-call overhead) and a code execution surface that requires sandboxing.
Actionable error guidance (Datadog technique): v3 implements fuzzy matching on field names — "Unknown field 'stauts' — did you mean 'status'?" — and contextual hints like "Showing 5 of 500 available." These don't show up in token benchmarks, but they reduce retry cycles dramatically. Agents recover well when told specifically what went wrong.

Winners by Query Type

The benchmarks reveal something the original blog posts don’t emphasize: no single pattern wins every scenario.
The sweet spot for production is v3 as the foundation — structured, safe, no code execution surface — with v2 as an opt-in escape hatch for queries that can’t be expressed as parameters. S
tructured tools handle 90% of queries. Code execution handles the 10% that need arbitrary logic.

The Counterargument

Models are getting smarter. Won’t they just handle raw APIs eventually?
Maybe — but that conflates two constraints. Tool selection is an intelligence problem, and it’s improving.
But fitting 1,891 tokens of raw stories into a context window when you need a 2-line summary is a resource problem.
A perfect tool-selector still can’t reason over data that doesn’t fit, and still wastes money transmitting tokens the agent will never use. The efficiency principles hold regardless of model intelligence.

Where to Start

If you’re building or refactoring an MCP server now, three moves will get you 80% of the benefit:
1. Measure your token footprint. Call your most-used tool with a typical query and count the response tokens. Then count how many the agent actually needed. In my benchmarks, the ratio was often 10:1 or worse. Have your MCP server re-serialize to CSV and trim unnecessary fields before returning results — even if the upstream API gives you JSON with everything.
2. Add one aggregation tool. Pick the question your users ask most — “compare X vs Y,” “what’s the average Z” — and build a tool that answers it directly. This produced the single largest improvement in my benchmarks: 98% token reduction for a comparison query. Your server can fetch, filter, and aggregate internally even if the underlying API doesn’t support it.
3. Watch an agent use your server. Not in unit tests. In a real session, on a real task. The 11-call fan-out in Scenario 3 looked fine in unit tests — each tool worked correctly. It was only watching the full session that revealed 1,578 tokens of waste. Every team whose lessons appear in this article learned the same way.
The MCP protocol standardized connectivity and authorization. What it didn’t standardize is how to design the tool surface. That’s what these benchmarks — and the production lessons from Datadog, Block, and Cloudflare — start to answer.
